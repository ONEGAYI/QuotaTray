# 自动更新预研：短期 NSIS 静默安装与长期双目录布局

- 日期：2026-08-28
- 背景：issue #58 请求「检测更新 → 自动下载 → 用户确认 → 自动安装 → 自动清理」的完整更新闭环。本文评估两条实施路线：**短期用 NSIS 静默参数低成本闭环**，**长期演进为 Chrome 式双目录版本化布局**（运行中一个版本、旁边装新版本、切换零打断）。
- 范围：Windows 桌面端安装版。便携版（zip 手动覆盖引导）与 CLI 侧更新不改变现有形态，仅说明受影响面。
- 结论效力：预研文档，未经所有者确认不构成实施决策。NSIS 安装器行为均**实证于 Tauri 2 官方 NSIS 模板源码**（见附录来源），非文档转述。

---

## 一、结论速览

| 路线 | 可行性 | 工作量 | 核心结论 |
|---|---|---|---|
| 短期：NSIS 静默安装 | ✅ 无架构障碍 | 约 1.5–2 人日 | Tauri NSIS 模板原生支持 `/S /UPDATE /R` 组合：全静默、跳过重装交互、装完自动重启应用；currentUser 安装模式全程无 UAC。改动集中在 spawn 参数、惰性清理与下载完成确认交互 |
| 长期：双目录版本化布局 | ✅ 有独特便利 | 1–2 周 + 长期维护 | 现有 `*-portable.zip` 资产本身就是全量应用包，日常升级**无需新增资产类型**；但要引入 junction 切换、NSIS 首装布局钩子、启动自检回退协议，并处理存量用户从平铺布局的一次性迁移 |

**实施路径**：短期方案在下个 minor 版本闭环 issue #58 → 长期方案挂起，待真实用户反馈
「常驻进程不可中断」构成痛点、或 ARM64 转正需要统一更新体验时再立项（见 §六触发条件）。

> 附注：issue 作者与本项目此前对话中提到的「和 VSCode 一样」需要事实修正——
> VSCode Windows 用户安装版的更新正是「退出 → 静默重装 → 重启」（Inno Setup 静默参数），
> 即本报告的短期路线；真正采用双目录布局的是 Chrome/Edge 与 Squirrel 系应用
> （Discord、GitHub Desktop）。两条路线的体验标杆各有其主。

## 二、现状盘点：issue 诉求与 v0.7.0 现状的差距

issue #58 的五项具体诉求，对照当前代码逐项核实：

| #58 诉求 | v0.7.0 现状 | 差距 |
|---|---|---|
| 下载完成后弹出安装确认 | 下载完成后设置页「更新」页签出现「安装」按钮，点击有 `confirmDialog` 二次确认（`SettingsDialog.tsx:181`）——但**不主动弹窗**，需用户自己回到设置页 | 需新增主动确认交互 |
| 确认后自动调用安装程序，无需手动找文件 | ✅ 已实现（`e35b3f7`，v0.4.1 起）：`install_update` → `run_installer` spawn 安装包 → 400ms 后应用退出（`commands.rs:1245`） | 已闭环；issue 作者应是在用旧版或未发现入口 |
| 安装完成后自动清理安装文件 | ❌ 无主动清理，注释口径是「随系统 Temp 清理自然回收」（`update_ctl.rs:93`） | 需新增惰性清理 |
| 「稍后安装」时保留安装文件 | ✅ 天然满足（任何路径都不删文件） | 无 |
| 安装失败时保留安装文件 | ✅ 天然满足 | 无 |

另外两个 issue 隐含但值得正视的点：

**「自动下载」其实不存在。** issue 作者以为「已支持自动下载」，实际下载是用户在设置页
手动触发（`download_update` 命令）。要完整复现 issue 期望的流程图，还需一个
「检测到新版本后自动下载」的选项（§4.4 决策点）。

**已下载状态是内存态，重启即丢。** `UpdateCtlState.downloaded` 不落盘
（`update_ctl.rs:51`）。应用重启后即使 Temp 里的安装包还在，状态表已清空——用户回设置页
看到的是「下载安装包」而非「安装」。安装失败重启的场景下，这会导致无谓的重新下载
（§4.3 探测恢复）。

## 三、NSIS 安装器能力契约（Tauri 2 模板实证）

以下行为全部实证于 `tauri-apps/tauri` 仓库 `crates/tauri-bundler/src/bundle/windows/nsis/`
下的 `installer.nsi` 与 `utils.nsh`（master 分支，2026-08-28 查证）。本项目
`tauri.conf.json` 的 `nsis` 节只设了 `installerIcon`，以下均为 Tauri 默认行为。

### 3.1 命令行参数

| 参数 | 语义 | 模板出处 |
|---|---|---|
| `/S` | NSIS 原生全静默：无任何安装 UI | NSIS 内建 `${Silent}` |
| `/P` | 被动模式：跳过全部向导页，保留进度窗口，装完自动关闭 | `.onInit` 解析 + `SkipIfPassive` |
| `/UPDATE` | 升级语义：重装确认页直接放行（明文 `Goto reinst_done`，不卸载旧版直接覆盖）；卸载旧版时保留快捷方式与自启注册表项 | `PageLeaveReinstall` / `Section Uninstall` |
| `/R` | 仅静默/被动模式下生效：安装成功后自动启动应用（`RunAsUser`，用户态） | `.onInstSuccess` |
| `/ARGS` | 与 `/R` 连用，给重启后的应用传启动参数 | `.onInstSuccess` |
| `/NS` | 跳过开始菜单与桌面快捷方式创建 | `CreateOrUpdate*Shortcut` |
| `/D=<dir>` | 指定安装目录（本场景不用，安装器按注册表恢复原目录） | `.onInit` |

### 3.2 与本项目直接相关的三个关键行为

**无 UAC。** 本项目未设 `installMode`，Tauri 默认 `currentUser`：模板生成
`RequestExecutionLevel user`，安装到 `%LOCALAPPDATA%\QuotaTray`。整个静默升级链路
**全程用户态**，不出现提权弹窗。

**静默模式下正在运行的应用会被自动结束。** `CheckIfAppIsRunning` 宏（`utils.nsh`）
找到目标进程后：静默模式（`IfSilent`）直接跳到 kill 分支执行
`KillProcessCurrentUser`（currentUser 模式只查杀当前用户进程，不碰其他会话）；非静默
非被动模式才弹 `MessageBox` 询问。kill 后失败（杀不掉）时静默模式下以非零码退出。

**静默升级不动快捷方式。** 模板在静默/被动模式下会主动补建桌面快捷方式，但
`/UPDATE` 置位时「开始菜单 + 桌面」的创建函数都直接 `Return`——升级场景快捷方式
原样保留。WebView2 的检测安装同样被 `/UPDATE` 跳过（升级假定首装已处理）。

### 3.3 参数组合决策：`/S /UPDATE /R`

推荐组合为 `/S /UPDATE /R`（顺序无关），理由：

- **必须带 `/UPDATE`**：裸 `/S` 遇到「检测到已安装版本」会走重装确认页的 nsDialogs
  分支——静默模式下该自定义页的交互控件无输入来源，走向属于未定义行为依赖。
  `/UPDATE` 是模板明文的「升级直接放行」路径。
- **`/R`** 负责装完自动拉起新版，用户全程只点一次「立即安装」。
- **暂不建议 `/NS`**：升级场景 `/UPDATE` 已使快捷方式创建跳过，`/NS` 冗余；
  留作未来若出现非升级静默场景再启用。

## 四、短期方案：NSIS 静默安装闭环

### 4.1 目标流程

```text
检测到新版本（现有调度，24h 节流 + 每日到点）
    ↓
自动下载安装包（可选开关，§4.4）→ 进度推送（现有事件）
    ↓
主动确认：「QuotaTray x.y.z 已就绪，立即安装？」[立即安装] [稍后]
    ↓  立即安装
spawn 安装包（/S /UPDATE /R）→ 应用 400ms 内正常退出（现有时序）
    ↓  （NSIS 静默覆盖安装 → 自动重启新版）
新版启动 → 惰性清理旧安装包
```

「稍后」与安装失败两条路径都依赖同一兜底：文件留在下载目录，重启后由探测恢复
免重新下载（§4.3）。

### 4.2 改动清单

| 层 | 改动 | 位置 |
|---|---|---|
| core | 新增「资产名 → 版本号」解析公开纯函数（复用 `parse_version` 语义） | `crates/quota-core/src/update.rs` |
| core | 新增惰性清理纯函数：给定下载目录文件列表 + 当前版本，返回应删文件（版本 ≤ 当前版本的资产文件） | 同上 |
| 桌面后端 | `run_installer` spawn 追加 `args(["/S", "/UPDATE", "/R"])` | `update_ctl.rs:304` |
| 桌面后端 | 启动时执行惰性清理 + 探测恢复（§4.3） | `lib.rs` 启动序 |
| 桌面后端 | 下载完成事件驱动前端确认（新增 emit 或复用 `UPDATE_STATE_EVENT`） | `update_ctl.rs` |
| 前端 | 下载完成确认弹窗（主窗可见时 `confirmDialog`；不可见时见 §4.4 决策点） | `SettingsDialog.tsx` / `App.tsx` |
| 前端 | 「自动下载更新」设置项 + i18n 双语文案 | 设置「更新」页签 |
| 测试 | 资产名解析、清理判定、探测恢复的契约测试（core 纯函数 + update_ctl 沙箱） | 各模块 tests |

**退出时序维持现状**（spawn → 400ms → `app.exit(0)`）：应用先走 Tauri 正常退出流程
（托盘图标干净移除、内存态正常收尾）优于被 NSIS 强杀；NSIS 的 kill 只是竞态兜底
（kill 一个正在退出的进程按模板语义同样放行）。

### 4.3 惰性清理与探测恢复

**惰性清理**取代 issue 字面的「装完立即删除」：应用退出后无人可执行即时清理，
而 Temp 语义本就是系统兜底回收。策略：**启动时扫描下载目录，删除资产版本号
≤ 当前运行版本的所有 `.exe`/`.zip`**。该策略同时满足 #58 的三条保留诉求——
安装成功（新版启动，旧包版本更低 → 删）、安装失败与稍后安装（旧版仍在运行，
新包版本更高 → 留）。

**探测恢复**解决「重启后已下载状态丢失」：`run_check` 成功得到 `asset_name` 后，
先探测下载目录是否存在同名文件，存在则直接写入 `downloaded` 记录、跳过下载。
比持久化状态表更简单——磁盘文件本身即状态，且天然覆盖「手动下载后重启」场景。

> 安全加固（可选，非本期必需）：Temp 为用户态任意进程可写区，下载完成时把
> 文件字节数记入旁车文件（或 settings），恢复时核对，防同权限进程替换文件。
> 属纵深防御，威胁模型与现状 `run_installer` 执行面相同，不构成新增风险。

### 4.4 决策点（需所有者拍板）

| 决策点 | 选项 | 推荐 |
|---|---|---|
| 自动下载默认值 | A. 默认开启（对齐 issue 期望与 VSCode 惯例，安装包 MB 级）/ B. 默认关闭（用户群体多走代理，流量自主权优先） | **B，默认关**：检测提示保留，下载一步可见可控；想全自动的用户可自行开启 |
| 主窗不可见时的确认呈现 | A. Windows 系统通知（点击唤起主窗确认）/ B. 直接 show 主窗弹确认 | **A**：托盘常驻应用打扰最小化；通知基础设施需评估 `tauri-plugin-notification` 引入成本 |
| 静默失败的可观测性 | 静默安装失败无任何 UI（见 §4.5），是否需要失败后首启提示「上次更新未完成」 | **暂不做**：探测恢复已免重下，重试入口顺滑；失败率预期极低 |

### 4.5 失败模式

| 场景 | 表现 | 兜底 |
|---|---|---|
| 静默安装中途失败 | 应用已退出，无 UI，新版未装上 | 用户经快捷方式/自启回到旧版；探测恢复使「安装」入口直接可用，一键重试 |
| 下载目录被系统清理 | `run_installer` 已有清记录 + 报错逻辑（`update_ctl.rs:294`） | 前端回到「下载」态，现有行为 |
| 用户取消确认 | 「稍后」后无提醒直至下次检测 | 可接受；通知策略随 §4.4 第二项定 |

### 4.6 工作量

约 **1.5–2 人日**：core 纯函数与契约测试 0.5 天，桌面后端接线 0.5 天，前端交互 +
i18n + 设置项 0.5 天，手动冒烟（真实静默升级一轮）0.5 天内。无打包链、发布资产、
CI 改动。

## 五、长期方案：双目录版本化布局（Chrome 式）

### 5.1 目标形态与体验

```text
%LOCALAPPDATA%\QuotaTray\
├── app-0.7.0\              ← 运行中的版本，升级全程不被触碰
├── app-0.9.0\              ← 后台下载解压就绪的新版本
└── Current ──(junction)──→ app-0.9.0
```

体验分两级：

- **就绪态零打扰**：新版解压完成即挂起，托盘提示「新版本已就绪」，不强制重启；
  用户下次自然重启（或点「立即重启」）时生效。这是**推荐形态**——托盘应用重启
  成本本就是秒级，且天然规避新旧双实例并存的竞态。
- **确认即切换**：用户点「立即重启」→ 切 junction → 拉起新版 → 旧版退出，
  中断窗口 1–2 秒，与短期方案同级。

### 5.2 复用 portable.zip：本项目的独特便利

日常升级的「新版本载体」**直接复用现有 `*-portable.zip` 发布资产**——它本身就是
全量应用包（GUI exe + `bin/quota.exe` + WebView2 loader），解压到 `app-<版本>\` 即完成
 staging。这意味着：

- 发布链与资产命名零改动（`expected_asset_name` 契约不变）；
- **ARM64 Preview 用户同样受益**——`arm64-preview-portable.zip` 已在发布矩阵中，
  而短期方案的静默安装仅覆盖 x64（NSIS 安装包仅 x64 发布）；
- NSIS 安装包退化为「首装 + 大跨度修复安装」专用。

代价是 core 的 `AssetSelector` 语义演进：安装版的**日常升级改选 `PortableZip` 资产**，
`SetupExe` 保留给首装/修复/跨布局场景——选择逻辑从「形态二选一」变为「版本与场景感知」，
这是本方案对 core 冻结 API 面的一次有理由的扩展，需按并行开发约定单独提 PR。

### 5.3 布局与切换的技术要点

**junction 而非 symlink。** `std::os::windows::fs::symlink_dir` 创建的是真符号链接，
需要 `SeCreateSymbolicLinkPrivilege`（开发者模式或管理员）；目录联接（junction）普通
用户即可创建，需引入 `junction` crate 或直接走
`DeviceIoCtl(FSCTL_SET_REPARSE_POINT)`。快捷方式、自启 `HKCU Run` 键统一指向
`Current\QuotaTray.exe`，切换后自动跟随，无需改写。

**NSIS 首装负责布局建立。** Tauri NSIS 模板默认把 exe 平铺进 `$INSTDIR`，要实现
「根目录只有 junction + 版本目录」，需通过 `bundle.windows.nsis.installerHooks` 提供
自定义 `NSIS_HOOK_POSTINSTALL`（挪文件、建版本目录与 junction、快捷方式指向
`Current\`）与 `NSIS_HOOK_POSTUNINSTALL`（清理全部 `app-*` 目录与 junction）。
这是一段需要长期维护的 nsh 脚本。

**存量迁移的坑：`/UPDATE` 不卸载旧版。** 存量平铺用户首次升级到「首个双目录版本」时，
`/UPDATE` 语义跳过旧版卸载，根目录的旧平铺 exe 会与新布局并存。解法：hook 脚本在
`POSTINSTALL` 显式检测并删除根目录旧平铺文件。此坑必须在首版迁移设计里显式处理，
否则出现「双入口」混乱。

### 5.4 提交与回退协议（两阶段提交）

junction 方案的天然弱点是回滚：崩溃中的进程没有机会切回。设计如下协议（细节立项时定）：

1. **就绪**：新版解压完成，写 pending 标记（含目标版本），junction 不动。
2. **提交**：启动早期逻辑读 pending → 切 junction → 启动新版 → 新版在托盘就绪后
   清 pending、更新注册表（`DisplayVersion` 等，HKCU 用户态可写）、延迟清理旧目录。
3. **回退**：新版首启若在健康窗口内连续失败 N 次（失败计数落盘），下次启动早期
   逻辑检测到即回切旧 junction 并弃用该版本目录，用户留在旧版并收到提示。

该协议把「提交点」放在新版自证健康之后，回退不依赖崩溃进程自救。前提是启动早期
逻辑位于 junction 链路之外（根目录或 `Current` 之外的稳定位置），这是布局设计里
最需要推敲的一环。

### 5.5 失败模式与风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 双实例并存 | 确认即切换的窗口期新旧两个托盘图标 | 推荐就绪态形态规避；若做即切需单实例互斥（本项目现状未见单实例锁，需立项确认） |
| junction 创建失败 | 杀软/策略限制 reparse point | 提交前预检；失败回退 NSIS 全量路径 |
| zip 布局漂移 | portable.zip 内部结构变化导致 staging 失败 | 打包契约测试已锁资产名，需补「zip 内布局」断言（`package.tests.ps1` 扩展） |
| 磁盘占用 | 双版本并存翻倍（每版 ~20–30MB） | 新版健康后延迟清理旧目录；可保留上一版用于回退 |
| NSIS hook 维护成本 | 自定义 nsh 脚本随 Tauri 模板升级的兼容性 | hook 尽量薄（只做挪移与 junction），安装逻辑仍走模板主体 |

### 5.6 工作量

**1–2 周**：自更新器子系统（下载解压、版本目录管理、提交/回退协议）约 4–5 天；
NSIS hook 与首装布局约 2 天；`AssetSelector` 演进与 core 契约测试约 1–2 天（单独 PR）；
迁移设计与全量回归约 2–3 天。另有持续性维护成本（hook 兼容、双路径测试矩阵）。

---

## 六、分期建议与触发条件

**短期方案立即排期**（下个 minor 版本）：工作量小、无资产与打包链改动、完整覆盖
issue #58 全部诉求，且体验与 VSCode 用户版同级。

**长期方案挂起，出现以下任一信号时立项**：

1. 真实用户反馈「常驻进程中断不可接受」（如查询任务、长时间挂机监控场景增多）；
2. ARM64 转正（WoA 验收通过），需要为 ARM64 用户提供与 x64 一致的自动更新体验；
3. 更新翻车率实际偏高，需要系统性回滚能力（双目录是唯一带回滚的方案）。

短期方案为长期留下的复用件：下载进度链路、惰性清理、探测恢复、确认交互——
双目录方案的「下载 staging」阶段可整体继承；`AssetSelector` 的形态分流也为
版本感知选择预留了清晰的原型。

## 七、安全对照（对照 AGENTS.md 安全红线）

更新链路不涉及凭据字段，红线 1–4 不受影响。需明确的是**执行下载 exe** 的风险面：

- **现状边界**：来源限定 GitHub Release（HTTPS）+ 资产名精确匹配 + 写入/运行双侧
  路径防御（`validate_asset_name` / `validate_installer_path`）。无端到端签名校验
  （项目无代码签名证书），与「HTTPS 传输完整性 + 用户显式确认」的行业基线一致；
  静默参数不改变该边界（执行仍以用户点「立即安装」为前提，与 issue #58 作者
  「必须确认、不静默执行」的要求一致——**静默的是安装器 UI，不是确认环节**）。
- **MotW 说明**：安装包由 reqwest 直写文件，不携带 Mark-of-the-Web，spawn 不会
  触发 SmartScreen 拦截路径。这只意味着「无弹窗」，不等于「已通过系统信任校验」。
- **增强项（两方案通用，可选）**：Release 附 SHA256 清单 + 安装/解压前校验，
  防传输损坏与缓存投毒；根治手段是代码签名（EV 证书成本项，另行决策）。
