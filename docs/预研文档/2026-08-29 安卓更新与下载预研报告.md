## 一、结论速览

| 议题 | 结论 |
|---|---|
| WoA 误匹配根源 | 确认：Android（aarch64）`arch_label()` 返回 `"ARM64"`，`for_runtime` 会选中 WoA 的 `arm64-preview.zip`。当前靠命令层守卫防住，**改造必须先于任何移动端更新 UI 放开** |
| 修复方式 | core 新增 `Flavor::AndroidApk` + `android-arm64` 资产段，选择器按 `cfg!(target_os = "android")` 编译期分流；APK 期望名 `QuotaTray_{v}_android-arm64.apk` 与 WoA zip 天然不同名，消歧零歧义 |
| 下载落盘 | 复用配置导出的 SAF 全链路：前端 `plugin-dialog save()`（Android 返回 `content://` URI）+ 后端 `tauri-plugin-fs` 打开 URI 写字节。两条先例均已在真机/模拟器实证 |
| 下载通道 | `ReqwestAssetDownloader` 直接复用（APK 18.1 MB，内存 `Vec<u8>` 方案在上限 256 MB 内富余）；进度事件 `update-download-progress` 跨端可用 |
| 安装引导 | **自动拉起安装器首期不可行**：tauri-plugin-opener 在 Android 打不开本地文件 / `content://` URI（plugins-workspace issue #2383）。首期下载完成后引导用户从文件管理器手动安装 |
| 检测调度 | Android 不启动常驻轮询（`spawn_scheduler` 现仅桌面编译）；首期口径「前台手动检测」——进入更新页自动检一次 + 手动「立即检查」 |
| 工作量 | core 资产选择 0.5–1 人日；命令层与前端 1.5–2.5 人日；真机验收贯穿。合计约 3–4 人日（缺口报告估 3–5 人日，SAF 先例使下限更低） |

## 二、现状锚点（核对于 `1dcdb0e`）

### 2.1 core 资产选择器（`crates/quota-core/src/update.rs`）

- `arch_label()`（:26）：`x86_64` → `"x64"`，`aarch64` → `"ARM64"`——**不区分 OS**，
  Android 与 WoA 同标签，这是误匹配的唯一根源。
- `Flavor` 三值（:38）：`SetupExe` / `StandaloneZip` / `PortableZip`，全部是
  Windows 分发物；`for_runtime`（:64）按「portable？→ arm64？→ x64」三段分流，
  Android 安装态会落入 `StandaloneZip`（WoA zip）。
- `expected_asset_name`（:94）：arm64 一律加 `preview` 段；`parse_asset_filename`
  （:114）的 arch 段白名单只有 `x64` / `arm64-preview`。
- `pick_asset`（:351）按期望名**完整相等**匹配、绝不回退——这意味着接入
  `android-arm64` 命名后，即使 release 里同时存在 WoA zip 也不会误命中；
  反过来说，**不改造 core 就放开 Android 检测，会精确命中 WoA zip 并引导
  用户下载无法使用的 Windows 包**（缺口报告 §五「放开即暴露」风险）。
- 版本比较（:256）为三段数字比较，与 Android versionCode 派生公式
  （`major*1e6 + minor*1e3 + patch`，CI 已断言）单调性一致，无额外工作。

### 2.2 命令层守卫（`commands.rs`）

| 命令 | 守卫 | Android 现状 |
|---|---|---|
| `get_update_state`（:1398） | 无 | 可调用，但状态表恒空（无检测执行过） |
| `check_update_now`（:1410） | `ensure_desktop_update_commands` | 确定性报错 `err_mobile_update_unsupported` |
| `download_update`（:1431） | 同上 | 同上 |
| `install_update`（:1441） | 同上 + 形态二次校验 | 同上（Android 永久不放开） |
| `open_update_dir`（:1357） | 同上 | 同上（Android 无目录概念，不放开） |

守卫函数 `desktop_update_commands_supported`（:1186）按 `target_os` 判定，
语义是「整套桌面更新命令」——放开检测/下载时需要拆分粒度，不能整体翻位。

### 2.3 调度器与自动下载（`update_ctl.rs` / `lib.rs`）

- `spawn_scheduler`（update_ctl.rs:513，每分钟 wake、5 分钟节流轮询）仅在
  桌面编译分支启动（lib.rs:95-99 `#[cfg(not(any(android, ios)))]`）——Android
  无任何更新事件源，前端 `update-ready` 监听空转（无害）。
- 桌面自动下载判定 `should_auto_download`（update_ctl.rs:388）含
  `!manual_update` 门禁；Android 首期不做自动下载（缺口声明口径「用户主动
  下载」），该判定不移植。
- 下载目录 `%TEMP%/QuotaTray/Downloads`（update_ctl.rs:104）与惰性清理
  `is_stale_installer` 在 Android 无对应语义（SAF 直写用户位置，不留缓存）。

### 2.4 前端

- 能力位 `selfUpdate: !mobile`（`runtimeView.ts:20`）；设置页回跳兜底
  `mobile && tab === "update"`（`SettingsDialog.tsx:79`）。
- 更新页已有完整状态机：状态查询（`useUpdateState`）、手动检测、下载进度
  监听（`update-download-progress` 事件）、`resolveUpdateStatus/Action` 纯逻辑
  ——移动端主要是动作层适配，展示层可复用。
- 设置项 `update_check_enabled` / `update_auto_download` / `update_proxy_port`
  三项在 Android 首期均无调度语义（手动检测不受节流）。

### 2.5 可直接复用的 SAF 先例（关键减益因素）

配置迁移链路已完成「前端选择 + 后端写入」的全套实证：

1. **前端 SAF save**（`SettingsDialog.tsx:148-160`）：`plugin-dialog` 的
   `save()` 在 Android 拉起系统文档创建器，`filters.extensions` 传 MIME
   （桌面传真实扩展名），返回 `content://` URI；
2. **后端写 content URI**（`commands.rs:276-306`）：`tauri_plugin_fs::FsExt`
   以 `OpenOptions`（write + truncate + create）打开 URI 写全部字节，
   `export_configuration_to_uri` 即此模式；
3. **ACL**：`mobile.json` 已含 `dialog:allow-save`；自定义 command 与
   Rust 侧 `FsExt` 调用均不受前端 capability 约束。

## 三、外部事实与查证

- **APK 体积**：v0.8.1 资产 `QuotaTray_0.8.1_android-arm64.apk` 实测
  18,990,306 字节（≈18.1 MB）。`AssetDownloader` 返回内存 `Vec<u8>`、
  上限 256 MB——内存方案富余约 14 倍，无需改 trait 或流式落盘。
- **opener 无法触发安装器**：tauri-plugin-opener 的 Android 实现走 URL
  打开路径，对本地文件 / `content://` URI 报「无 Activity 可处理」
  （plugins-workspace [issue #2383](https://github.com/tauri-apps/plugins-workspace/issues/2383)）。
  要在下载完成后自动拉起系统安装器（`ACTION_VIEW` + APK MIME +
  读授权 flag），需要第三方 intent 插件或自研 Rust-JNI 桥——两者都超出
  首期投入意愿，列为后续可选项。
- **SAF 写入 Downloads 后的系统行为**：用户经 `ACTION_CREATE_DOCUMENT`
  选定位置（通常在 Downloads）后，部分系统会在通知栏提示下载完成，
  但**不保证**可点击安装——不同厂商行为不一，不能作为依赖项，UI 必须
  给出确定性的手动引导文案。
- **网络栈**：真机查询正常已实证 reqwest + rustls 在 Android 可达外网
  （含 GitHub API 使用的 TLS）；`User-Agent` 要求与桌面同源，无 Android 特判。

## 四、方案设计（分三段，依赖有序）

### 4.1 core：资产选择接入 `android-arm64`（先行，独立合入）

1. `Flavor` 新增 `AndroidApk` 变体（`requires_manual_update` 返回 true——
   语义上 Android 一律手动安装）。
2. `for_runtime` 增加编译期分支：`cfg!(target_os = "android")` 时恒为
   `AndroidApk`（Android 无安装/便携形态之分，`portable` 参数在该分支
   无效——Android 便携概念不存在，`RuntimeMode` 在移动端恒 Installed）。
3. `expected_asset_name`：arch 段 `android-arm64` 不加 `preview` 段
   （Android Preview 口径由 Release 文案表达，不进资产名——与
   `android-release.yml` 既有命名一致），后缀 `.apk`。
4. `parse_asset_filename`：arch 白名单加 `android-arm64`、后缀判定加
   `.apk` → `AndroidApk`；注意判序（`.apk` 与既有后缀无前缀包含关系，
   无歧义）。
5. 契约测试：正向拼装与反向解析镜像、Android 选择器命中 APK 而非
   WoA zip、`arch_label` 在 Android 仍返回 `"ARM64"`（展示层标签）但
   选择器已分流。
6. 顺带：`UpdateStateDto.platform` 在 Android 显示 `"ARM64"` 易与 WoA
   混淆，端侧展示宜加平台标识（实现时定，非 core 职责）。

**发布顺序约束**：core 合入前，Android 端任何更新 UI 不得放开——守卫
是唯一防线，此约束已由缺口报告 §五登记，实施 PR 按段拆分即天然满足。

### 4.2 命令层：拆守卫粒度 + Android 下载变体

1. `ensure_desktop_update_commands` 拆为两级：
   - `ensure_update_check_supported`：桌面 + Android 放开（`check_update_now`）；
   - 原名保留给 `install_update` / `open_update_dir`（永久桌面）。
2. `check_update_now` 在 Android 分支：跳过托盘重建（`tray::rebuild` 桌面
   专属）与 `post_check`（自动下载不移植）；其余逻辑（run_check、状态表、
   节流时间戳落盘）跨端复用。
3. 新增 `download_update_to_uri(uri: String)`（Android 专用）：下载字节
   （复用 `ReqwestAssetDownloader` + 进度 reporter）→ 校验资产名 →
   `FsExt` 写入 content URI（模式照抄 `export_configuration_to_uri`）。
   桌面 `download_update` 不动。
4. 资产名写入校验 `validate_asset_name` 需扩 `.apk` 后缀（桌面语义的
   exe/zip 校验在 Android 分支外，不混用）。
5. 守卫语义不变的部分显式留测试：`install_update` / `open_update_dir`
   在 Android 仍确定性报错（Play 红线的代码面表达）。

### 4.3 前端：更新页移动化

1. `runtimeView.selfUpdate` 翻位（android true）；移除回跳兜底。
2. 更新页动作按平台分流（`resolveUpdateAction` 纯逻辑扩平台参数）：
   - **检测**：进入更新页自动检一次（`check_update_now`）+ 手动按钮，
     不做常驻轮询；
   - **下载**：`save()` 拉起 SAF（`defaultPath` 建议文件名，MIME
     `application/vnd.android.package-archive`）→ 调
     `download_update_to_uri`；进度条复用既有事件与 `formatDownloadProgress`；
   - **安装**：不提供按钮；下载完成后展示引导文案（「已保存，请从文件
     管理器 / 下载项点击安装」），并为「安装未知应用」系统授权页给一句
     预期说明（厂商差异，属文案非代码）。
3. 设置项三项（自动检测开关 / 自动下载开关 / 代理端口）在移动端隐藏
   或禁用标注（首期无调度语义；代理端口保留可用性待真机验证后定）。
4. 无资产命中（release 未带 APK）时走既有「引导去发布页」路径——
   `html_url` 经 opener 打开（该路径已跨端可用）。

### 4.4 明确不做（首期）

- 自动拉起安装器（opener 限制，见 §三）；
- 自动下载与常驻轮询（Android 惯例 + 缺口声明「用户主动下载」）；
- 下载缓存目录与惰性清理（SAF 直写，无缓存语义）；
- `REQUEST_INSTALL_PACKAGES` 声明（红线：GitHub 通道用户手动安装不需要；
  该权限属于 Play 审核高危项）。

## 五、风险与红线

- **WoA 误匹配是唯一「放开即暴露」风险**：4.1 必须先于 4.2/4.3 合入
  （PR 拆分天然保序）。core 契约测试需覆盖「同一 release 含 WoA zip 与
  APK 时 Android 选择器只命中 APK」。
- **安装器红线**：不声明 `REQUEST_INSTALL_PACKAGES`、不内置任何安装
  逻辑；Play 构建变体若未来立项，本链路整体不进入。
- **SAF 位置多样性**：用户可选任意位置（含不支持的位置），写入失败
  需给确定性错误文案；`save()` 的 `defaultPath` 在 Android 的预填效果
  厂商不一，文件名以用户确认为准。
- **节流时间戳共享**：`update_last_check` 落盘在两端共用同一 settings
  字段——Android 手动检测也会刷新时间戳，对桌面轮询无影响（间隔仅
  5 分钟），反向亦然。无需拆分。
- **验收**：模拟器走通「检测 → SAF 保存 → 文件管理器安装」全链后，
  真机重复（含厂商浏览器外的文件管理器差异）；覆盖安装验收仍待
  下个正式版本发布（活追踪既有条目）。
