# 安卓缺口调研：Preview 端到可发布的能力差距盘点

- 日期：2026-08-29
- 背景：#61（`0ea34b0`）已交付 Android 触摸优先 Preview 端，首期能力（三类 Provider、配置迁移、Keystore 主密钥、前台刷新）闭环。移动端能力缺口追踪（时在 AGENTS.md，2026-08-30 起为 docs/移动端能力缺口追踪.md）登记了八项未纳入稳定能力的事项，本文逐项核对代码现状、定位根源、梳理相互依赖，作为后续移动端计划的现状底稿。
- 范围：仅 Android 端；桌面端事实仅作对照，不展开。iOS 不在目标平台内。
- 结论效力：预研文档，未经所有者确认不构成实施决策。全部现状锚点核对于 `9491f61` 工作树；量级为初步人日估计，仅供排序参考。

## 二、跨端基座现状

八项缺口共享同一套基座，先集中说明，后续各节不再重复。

### 2.1 平台判定与能力位

平台由后端声明，不由窗口尺寸或指针类型推断（T-010 规范）：Android 编译期
`runtime_platform_for` 固定返回 `"android"`（`commands.rs:1178`），经
`BootStateDto.platform` 传给前端 `runtimeUiPolicy`（`runtimeView.ts:18`）。

能力位层面 `RuntimeUiPolicy` 共 10 个字段：mobile 平台标志 + 9 个能力位。截至
核对时点（`9491f61`），移动端取反的 7 个：`hover` / `titleBar` / `tray` /
`autostart` / `selfUpdate` / `cliAssist` / `consoleLink`（其中 `consoleLink` 已于
2026-08-29 翻位为两端恒真，进度口径见 AGENTS 活追踪）；移动端为真的 2 个：
`fullScreenDialogs` / `bottomNavigation`。移动端启用任何桌面能力（如控制台直达）
都从翻转对应能力位开始。

### 2.2 命令层守卫

关键事实：**invoke_handler 两端注册同一套命令**（`lib.rs:235-270`），移动端不裁剪
命令表——一切「移动端不支持」都由命令内部守卫表达，前端隐藏只是体验层而非安全边界。

| 守卫 | 锚点 | 行为 |
|---|---|---|
| 更新命令拒绝 | `desktop_update_commands_supported`（`commands.rs:1190`） | Android/iOS 上检测、下载、打开下载目录、安装命令一律确定性报错（`err_mobile_update_unsupported`） |
| CLI 凭据平台拦截 | `mobile_cli_provider_blocked`（`commands.rs:1186`） | 依赖 core `uses_cli_credentials`（`provider/mod.rs:116`），Android 查询返回确定性错误 |
| 自启动拒绝 | `apply_autostart` 移动分支（`commands.rs:1216`） | 返回 `err_mobile_autostart_unsupported` |
| SAF 文档 URI | `is_android_document_uri`（`commands.rs:256`）+ `android_transfer_temp`（`:261`） | 配置导入导出走 `content://` 分支，迁移包字节不回传 WebView |

桌面专属的托盘 / 悬停窗 / 圆环在移动端由 `tray_mobile.rs`、`hover_panel_mobile.rs`
空实现替换（`lib.rs:9-24`），`update_ctl` 调度器仅桌面启动（`lib.rs:98`）——移动端
不存在更新事件源。

### 2.3 构建链现状

- **工具链矩阵**：workspace MSRV 1.88 / CI 锁 1.98.0（`rust-toolchain.toml`）/ JDK 17 /
  Android SDK 36 + Build-Tools 36.0.0 / NDK 27.2.12479018 / minSdk 24。
- **CI 命令链**（`ci.yml` android-preview job）：`pnpm android:init` →
  `pnpm android:build -- --ci --debug --apk --target aarch64`，产出
  **debug APK**（ARM64 单 ABI），以 artifact `QuotaTray-android-arm64-preview-debug`
  上传；无签名步骤、无 Release 上传。
- **工程生成加固**：`android-post-init.mjs` 在 `tauri android init` 后做三件事——
  Manifest 关闭自动备份（`allowBackup=false`）、注入 Keyring JNI 桥接类、在
  `MainActivity.onCreate` 的 `super` 之前调用 `initializeNdkContext`——均有契约测试
  锁定。`gen/android` 生成目录不入库，CI 每次重建以验证可复现。
- **交叉编译依赖**：reqwest 走 rustls（不依赖 openssl）；rquickjs 在 Android 追加
  bindgen feature，sysroot 环境变量由 `android-tauri.mjs` 从 `NDK_HOME` 推导。
- **版本与包名**：两份 tauri conf 均无 `version` 键，回退 workspace 版本（当前
  0.7.0），两端天然同源；Android 包名独立为 `com.quotatray.android`。

## 三、逐缺口分析

### 3.1 更新与下载 —— 存在与 WoA 资产的名称冲突根源

这是八项缺口中唯一有**代码级冲突根源**的，先说结论：

> Android 目标是 aarch64，`arch_label()`（`update.rs:31`）会返回 `"ARM64"`；
> `AssetSelector::for_runtime("ARM64", false)` 选中 `Flavor::StandaloneZip`
> （`update.rs:69`），`expected_asset_name` 产出 `QuotaTray_{v}_arm64-preview.zip`
> （`update.rs:99`）——**与 WoA Preview 资产完全同名**。换言之，若在 Android 上
> 放开更新检测而不改 core 资产选择，会精确匹配到 WoA 的 zip 并引导用户下载一个
> 无法使用的 Windows 包。

当前该风险**未激活**：`desktop_update_commands_supported` 在命令层前置拒绝全部更新
命令（§2.2），前端也隐藏更新页（`selfUpdate=false`；`SettingsDialog.tsx:79` 的
`mobile && tab === "update"` 回跳兜底）。但这也意味着「接入 Android 更新」不是打开
开关，而是三段工作：

1. **core 资产选择**：为 Android 增设独立资产形态（现有 `Flavor` 三值均指 Windows
   分发物，`update.rs:43-50`），命名契约与 `parse_asset_filename` 反向解析需同步；
2. **GUI 前台链路**：更新检测复用 `update_ctl` 的状态表与节流逻辑，下载改为系统
   文档选择器（SAF）落盘 + 进度反馈——桌面「下载到 Temp 后 NSIS 静默安装」的链路
   不适用（既定决策：#60 静默安装不移植到移动端）；
3. **安装引导**：普通自更新不得声明 `REQUEST_INSTALL_PACKAGES`（§五红线），用户
   主动下载 APK 后由系统安装器接管。

前置依赖：§3.2 签名链——没有固定签名的 Release APK，就没有可安装的更新目标。

### 3.2 签名与发布链 —— 从零起步，且是更新链的硬前置

现状是一片空白，且这个空白**阻塞 §3.1**：

- 全仓库 grep 无任何 keystore / signingConfig / apksign / versionCode 实现（scripts/
  与 src-tauri/ 均为空）；唯一相关记载是 AGENTS.md 缺口声明本身。
- CI 产物是 Tauri 隐式 debug 签名的 APK，换机器或清缓存后签名即变，无法覆盖安装。
- 跨版本覆盖安装（同签名下旧版本升级）从未验证——这依赖固定签名先存在。
- versionCode 无显式管理：Tauri 对 Android versionCode 的生成规则与跨版本单调性
  需在计划阶段查证，不能默认 workspace 三段版本直接可用。

工作量主体是发布工程而非代码：生成并安全保管长期签名密钥（密钥不入库——安全红线
同样适用于签名材料）、CI 增加 release 变体与签名步骤、gh release 上传与资产命名、
覆盖安装验证。`package.ps1` 的桌面逐 exe 架构断言模式可参考用于 APK 校验。

### 3.3 分发通道分流 —— 纯决策约束

无代码工作，两条通道的边界已由既定决策划定：

- **GitHub Preview 通道**（先行）：提供 APK 检测与用户主动下载，复用 §3.1 链路。
- **Play 通道**（挂起）：必须改走 Play Core 更新流程；普通自更新不得声明
  `REQUEST_INSTALL_PACKAGES`，商店外 APK 安装逻辑不得进入 Play 构建。

计划阶段需要回答的只有一件事：Play 版是否、何时立项。立项前所有更新设计只对
GitHub 通道负责，但接口设计应避免把「商店外安装」写死进公共路径。

### 3.4 消息中心与通知 —— 入口缺失与模型待扩

桌面链路（#60）的形态：后端 `update-ready` 事件 → 前端入列 → 标题栏铃铛 + 未读
红点 + 消息卡片，主窗不可见时补系统通知。移动端的差距在两层：

- **入口层**：消息中心挂在 `TitleBar`（`TitleBar.tsx:124`），而 Android 不渲染
  TitleBar，`MobileTopBar` 只有设置与添加两个动作（`App.tsx:174-179`）——消息在
  移动端**没有常显入口**。既定要求是顶部应用栏提供触摸可达的常显入口。
- **模型层**：`CenterMessage` 目前仅 `update-ready` 一种（`messageCenterView.ts:7`），
  且依赖桌面更新调度产生事件；移动端适用的消息类型（低余额提醒？查询失败？）需要
  重新定义，不能默认搬运桌面集合。

两个对计划有利的基础事实：

- 通知插件（`tauri-plugin-notification`）三端均已初始化（`lib.rs:181`），桌面侧已有
  Rust 调用先例（`update_ctl.rs:454`）；Rust 侧调用不受前端 ACL 约束。
- 前端 `update-ready` 监听是无条件挂载（`App.tsx:65`）——移动端因后端不调度而无
  事件，无害；扩展消息类型时该监听可继续复用。

待查证项：Android 13+（targetSdk 33+）的 `POST_NOTIFICATIONS` 运行时权限如何接入
（Tauri notification 插件的 Android 行为需实证）；通知的点击行为与前后台生命周期
联动（AGENTS 缺口声明明确要求覆盖）。

### 3.5 后台刷新 —— 承诺即现状，WorkManager 单独立项

现状是「承诺与实现一致」：文档只承诺前台轮询，实现上前台轮询依赖 React Query 的
`refetchInterval`（`queries.ts:84` 的 `refetchIntervalInBackground: true` 是桌面托盘态
语义），Android 上 WebView 随进程挂起即停止——没有任何代码在违背承诺。

后续工作按既定决策「WorkManager 单独立项」推进，计划阶段需回答：

- 系统允许的最小周期（Doze 模式下约 15 分钟且触发时刻不精确）与桌面「分钟级」
  承诺的分界如何表述；
- 后台任务的网络 / 省电约束策略，以及应用回前台后的补查语义（当前
  `refetchOnWindowFocus` 在 Android WebView 恢复时的实际行为待真机验证）；
- 后台刷新是否产生通知联动（与 §3.4 的消息模型设计交叉）。

### 3.6 桌面 CLI 凭据来源 —— 已闭环，定性为持续约束

Claude / Codex / Gemini / Grok 四类订阅查询依赖桌面 CLI 登录文件，移动端的处理已经
**三层闭环**，实现与文档口径一致：

1. 新增选择器列表过滤：`availableNativeMetas` 在 mobile 时剔除 CLI 凭据平台
   （`EditDialog.tsx:113-122`，存量编辑条目例外保留）；
2. 存量条目兜底：迁移带入的条目选中后显示警告并禁用保存（`mobileCliUnsupported`，
   `EditDialog.tsx:127`）;
3. 后端查询拦截：`mobile_cli_provider_blocked` 返回确定性错误（`commands.rs:1186`）。

因此本项不应再列为待实现缺口；保留为持续约束——未来若接入移动端等价授权（如
OAuth 设备流），必须单独评估凭据来源与安全边界，不属于任何既有缺口的范围。

### 3.7 控制台直达 —— 差启用三件事，可先行

#59 桌面端已合入（`9491f61`），移动端的**数据层与命令层已经跨端就绪**：

- `console_url` 字段、`NativeMeta` 预置值透出、编辑表单字段均已就绪；
- `open_console_url` command 注册在两端共用的 invoke_handler 中，Rust 侧 scheme
  校验与平台无关——移动端**不需要**扩充 `mobile.json` 的 opener ACL（该 scope 只
  约束前端 JS 直调，command 走 Rust 侧 opener）。

启用只差三件事（AGENTS 缺口声明的原口径）：

1. 翻转 `runtimeView.consoleLink`（`runtimeView.ts:15`，当前 `!mobile`）；
2. 图标钮触摸热区 ≥ 44×44px（T-010 规范；桌面实现是 26px 视觉尺寸的迷你档图标钮，
   移动端需按「视觉可小、热区足大」处理）；
3. opener 拉起系统浏览器、返回栈交互的真机验证。

体量小、独立、无依赖，适合作为移动端下一项的先行任务，并顺带开启 §3.8 的第一轮
真机验收。

### 3.8 真实设备验收 —— 贯穿始终的验收线

现状：仅 API 36 Pixel 8 x86_64 模拟器（ARM 转译）冒烟通过。验收清单已定义于
`docs/Android端预览版说明.md` §构建与验收（首次建库、重启解密、三类 Provider 查询、
前后台切换、触摸展开、图表拖动、导入导出、清空数据、深浅主题、双文布局）。

AGENTS 另列的未验项（safe-area 实效、宽视口、选择器外点关闭、返回键 history 栈、
系统回收、文档 URI 迁移、通知、下载、跨版本升级、厂商系统与实体 ARM64 设备）应
并入同一份清单管理。定性：这不是一次性任务，而是**每个能力启用节点的验收门槛**
（控制台直达、更新下载、通知各自触发对应子项），最终「转稳定」仍需所有者重新确认。

| 期 | 内容 | 触发条件 / 说明 |
|---|---|---|
| 一 | 控制台直达开启 + 真机验收启动 | 无依赖；同批完成 3.7 三件事与首轮真机清单 |

| 挂起 | WorkManager 后台刷新、Play 分流 | 各自单独立项（既定决策）；后台刷新的通知联动并入三期设计 |

## 五、风险与红线

- **WoA 误匹配是唯一「放开即暴露」的风险**（§3.1）：当前防线是命令拒绝，任何绕过
  守卫直接启用检测的改动都会命中同名资产。资产选择改造必须先于任何移动端更新
  UI 工作。
- **签名材料即密钥**：长期签名密钥的生成与保管遵循「源码零密钥」红线同等纪律，
  不入库、不进 CI 明文日志；丢失签名等于失去升级通道。
- **Play 红线**：`REQUEST_INSTALL_PACKAGES` 声明与商店外安装逻辑不得进入 Play 构建
  的任何变体。
- **凭据红线沿用**：Keystore 保护主密钥、`allowBackup=false`、迁移包字节不回传
  WebView——三项已有契约测试锁定，任何移动端改造不得绕过。
- **Preview 纪律**：真机完整验收 + 所有者重新确认前，Android 一切能力保持 Preview
  口径，Release 资产名与说明不得宣称稳定。
