# QuotaTray 项目方案预研

> 状态：预研草案（2026-08-22），实现以各里程碑验收为准；引用的 cc-switch 机制详见 [CC-Switch调研报告.md](CC-Switch调研报告.md)

## 1. 定位与目标

**一句话**：托盘常驻的多平台 AI 账户余额监视器——预置官方平台查询 + 声明式模板/JS 脚本自定义查询；GUI 是薄层，业务核心与 CLI 平级共享。

**目标**

- 常驻托盘，一眼看到各平台余额/配额（悬停刷新、菜单展示）
- 余额查询通用化：预置常见官方平台（Rust 原生），其余平台用声明式模板（零代码）或 QuickJS 脚本（兜底）自助接入
- 纯 CLI 可用：无 GUI 环境下完成查询、配置、模板管理
- 凭据不落明文：密文落盘、密钥托管系统凭据库，开源不泄漏

**非目标**（明确不做，属 cc-switch 的领地）：供应商切换与配置写入、本地代理/故障转移、MCP/Prompts/Skills 管理、用量日志统计仪表盘。QuotaTray 只做"读余额"，不碰任何 CLI 的配置文件——这正是凭据可以全程密文的原因。

## 2. 设计决策记录

四项决策已确认（快照另见 [AGENTS.md](../AGENTS.md)），此处补记理由：

| # | 决策 | 理由 | 放弃项的放弃原因 |
|---|---|---|---|
| D1 | Rust workspace 三端共享 | keyring / QuickJS / Tauri 托盘在 Rust 生态均成熟；core 编译一次，CLI 与 GUI 同源 | 异构 GUI 引入双语言双工程；Go/Node 在沙箱与凭据库环节生态弱 |
| D2 | 系统库存主密钥 + AES-GCM | 密钥随机生成（每机器独立）、托管系统凭据库（稳定、源码零密钥）；AES-GCM 为标准 AEAD，不暴露密文等值信息 | AES-SIV 等值比较收益对本场景小；凭据直存系统库有条目大小/枚举限制；DPAPI 绑定 Windows |
| D3 | 声明式模板优先 + JS 沙箱兜底 | 多数平台是"GET + header + 取字段 ± 算术"，声明式可覆盖且零脚本风险；复杂平台（多窗口聚合、特殊签名）由脚本兜底 | 全 JS 每个查询都是代码、审计面大；纯声明式遇到复杂平台就死路 |
| D4 | Windows 优先、代码不锁死 | 开发环境为 Windows；keyring/Tauri 等天然跨平台，不为未支持平台花测试打包工作量 | 仅 Windows 会锁死路径；三平台同步工作量翻数倍 |

## 3. 架构设计

### 3.1 Workspace 布局

```
QuotaTray/
├── Cargo.toml               # workspace 根
├── crates/
│   └── quota-core/          # 业务核心库（无 UI 依赖，可独立发布）
│       ├── provider/        # Provider 抽象 + 注册表（native / template / script 三类）
│       ├── query/           # 查询引擎：调度、超时、错误分类、keep-last-good
│       ├── template/        # 声明式模板解析与执行
│       ├── script/          # QuickJS 沙箱（{request, extractor} 协议）
│       ├── vault/           # 凭据保险库：keyring 主密钥 + AES-GCM 加解密
│       ├── model/           # UsageData 等统一数据模型
│       └── config/          # 配置读写（含密文字段编解码、迁移）
├── apps/
│   ├── quota-cli/           # CLI 前端（clap）
│   └── quota-desktop/       # Tauri 2 GUI 前端 + 托盘（薄层）
└── docs/
```

### 3.2 三端关系

```
             ┌─────────────┐   ┌──────────────────┐
             │  quota-cli  │   │  quota-desktop   │
             │ (clap, 平级) │   │ (Tauri 2 + 托盘)  │
             └──────┬──────┘   └────────┬─────────┘
                    │     均为普通依赖    │ invoke / emit
                    └────────┬──────────┘
                        ┌────┴─────┐
                        │quota-core│  ← 全部业务逻辑（查询/加密/配置）
                        └──────────┘
```

要点：

- **CLI 不是 GUI 的附属**：二者都是 quota-core 的普通消费者，core 不感知前端形态。
- **GUI 薄层的边界**：desktop 端只做展示与输入转发；所有查询、解密、模板解析在 core 完成，前端事件拿到的是 `UsageData` 结果而非凭据（红线见 AGENTS.md §安全红线 3）。
- Tauri 场景下无需独立 sidecar 进程：Rust 主进程即后端。若未来需要"无 GUI 常驻服务 + 多客户端"，可将 core 包一层本地 HTTP（届时另立决策）。

### 3.3 配置存储

单文件 JSON（`~/.quotatray/config.json`，Windows 下亦然），人工可读可备份；凭据字段为 AES-GCM 密文（`v1:<base64(nonce||ciphertext||tag)>`）。不引入 SQLite——数据量（个位数供应商 × 少量字段）不值当。

## 4. 凭据安全方案

### 4.1 密钥层级与流程

```
系统凭据库（Windows Credential Manager，经 keyring crate）
  └─ QuotaTray 主密钥：32B 随机，首次运行生成，永不落盘明文
        │ AES-256-GCM
        ▼
config.json 中的凭据字段（v1: 密文，含 nonce 与版本号）
```

- **主密钥生命周期**：首次运行 `os_rand(32)` 生成 → 写入系统凭据库（条目名 `QuotaTray`）→ 之后每次启动读取。每台机器天然不同；重装系统/删除凭据条目会导致密文不可解，属预期行为（提供"重置并重新录入"路径）。
- **密文格式带版本号**：未来算法升级（如换 SIV、换 KDF）可平滑迁移。
- **完整性**：GCM 自带认证标签，篡改即解密失败。

### 4.2 威胁模型

| 威胁 | 是否防御 |
|---|---|
| 源码公开后攻击者离线推算密钥 | ✅ 密钥与源码零关联（纯随机 + 系统托管） |
| 配置文件被拷走（备份/同步/共享屏幕） | ✅ 只有密文，离开本机不可解 |
| 同机其他普通权限进程读取系统凭据库 | ❌ Windows 凭据管理器按用户隔离，同用户进程不在防御范围（与浏览器保存密码同一水位） |
| 内存攻击 / 本机恶意软件 | ❌ 超出桌面工具防线，不做承诺 |

### 4.3 红线

见 [AGENTS.md §安全红线](../AGENTS.md)。补一条实现细节：错误信息与日志中涉及凭据的一律以 `sk-****<尾4位>` 形式呈现（继承 cc-switch 的掩码约定）。

## 5. 查询体系

### 5.1 Provider 三类抽象

```
ProviderConfig（每条供应商配置）
├── kind: "native"      → provider_id 指向内置实现（如 "deepseek"）
├── kind: "template"    → 内嵌声明式模板 JSON
└── kind: "script"      → 内嵌 {request, extractor} 脚本
```

三类共享同一凭据注入接口（`{{apiKey}}`、`{{baseUrl}}` 等变量替换）与同一结果模型。

### 5.2 统一结果模型（继承 cc-switch 约定）

```rust
pub struct UsageData {
    pub plan_name: Option<String>,
    pub total: Option<f64>, pub used: Option<f64>, pub remaining: Option<f64>,
    pub unit: Option<String>,            // "USD" / "CNY" / "%"
    pub is_valid: Option<bool>, pub invalid_message: Option<String>,
    pub extra: Option<serde_json::Value>, // resetTime / planLabel 等结构化附加信息
}
// 查询结果 = Vec<UsageData>（多窗口/多套餐时为数组）
// 百分比统一为"已用百分比"(0-100)
```

### 5.3 错误分类与刷新策略

- 错误分两类（继承 cc-switch 双轨制）：`Transient`（网络/超时/5xx/429 → 可重试，触发 keep-last-good）与 `Deterministic`（401/解析失败/未配置 → 立即透出）。
- 定时轮询间隔按 provider 可配（分钟级，默认 5）；托盘悬停触发即时刷新（节流 10 秒）。
- **改良点**：快照轻量持久化（`~/.quotatray/cache.json`，含时间戳），重启后托盘先显示旧值再异步刷新，消除 cc-switch 的"重启空窗"。

### 5.4 声明式模板 DSL（草案）

目标覆盖"一两个请求 + 字段映射 + 算术"型平台：

```json
{
  "request": {
    "url": "{{baseUrl}}/v1/user/info",
    "headers": { "Authorization": "Bearer {{apiKey}}" }
  },
  "extract": {
    "remaining": "$.data.totalBalance",
    "unit": { "const": "CNY" },
    "planName": { "const": "SiliconFlow" }
  },
  "transforms": [
    { "op": "multiply", "field": "remaining", "by": 0.01 }
  ],
  "windows": []
}
```

- `extract`：JSONPath 取值或常量；`transforms`：受限算术（multiply/divide/add/sub/round）；`windows`：多套餐展开（每窗口一条 `UsageData`，如 Kimi 的 5h + 周）。
- 校验：模板在保存时做静态校验（路径合法性、未知字段拒绝），执行期无 eval。
- **安全默认**：模板仅允许 HTTPS（loopback 除外）与 `{{baseUrl}}` 同源；放开限制需显式 `"allowInsecure": true`（GUI 中带警告）。

### 5.5 JS 脚本兜底

完整继承 cc-switch 协议（`{request, extractor}` 两阶段 + `{{变量}}` 注入 + 宿主发请求），沙箱限制不低于参考实现：内存 16MiB、CPU 5 秒中断器、无网络无文件系统。脚本声明的 URL 走与模板相同的同源/HTTPS 校验。

## 6. CLI 设计（子命令草案）

```
quota list                      # 列出全部 provider 及最近一次查询结果摘要
quota query [<id>...]           # 查询全部或指定 provider，表格输出
quota query <id> --watch        # 轮询模式（--interval 覆盖默认）
quota add / remove / edit <id>  # 供应商管理（交互式或 --json 传入）
quota template                  # 模板管理：list / test / import / export
quota script                    # 脚本管理：同上
quota vault                     # 主密钥与凭据：status / reset / export-warning
quota tray                      # 由 desktop 二进制承担，CLI 不做托盘
```

输出支持 `--json`（供脚本消费）与人读表格两种；退出码区分瞬时/确定性失败（后者非零，前者可配）。

## 7. GUI 与托盘设计

- **托盘**（核心界面）：菜单按 provider 分组展示"名称 + 剩余额度/已用百分比 + 相对时间"；悬停触发刷新（10 秒节流）；余额低于阈值时图标/条目变色提醒。
- **主窗口**（薄层）：provider 列表 + 添加/编辑表单（native 下拉 / 模板编辑器 / 脚本编辑器三形态）+ 刷新设置。关闭即收托盘。
- 前端选型跟随 Tauri 默认生态（React 或 Svelte 均可，M3 时定），原则：不引入重状态库，服务端状态直接消费 core 事件。

## 8. 里程碑

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| M0 骨架 | workspace + CI + 本文档体系 | `cargo build/test --workspace` 绿；空 CLI 可打印版本 |
| M1 核心查询 | quota-core：model/vault/query + 2~3 个预置平台（DeepSeek、SiliconFlow、OpenRouter） | 单测（mock HTTP）覆盖解析与加解密；密文落盘格式带版本 |
| M2 CLI | 全部子命令 + 模板 DSL | 纯 CLI 完成增删查改与模板测试 |
| M3 桌面端 | Tauri + 托盘 + 悬停刷新 + 快照持久化 | 托盘常驻展示，重启无空窗 |

> **M2 拆分与并行**（2026-08-23）：M2 中的 core 模板模块已提前完成（M2a，
> template DSL + 静态校验 + 执行器，64 测试），core 的 M2 API 面就此冻结；
> CLI（M2b）与桌面端（M3）现可双工作树并行开发，互不依赖。
| M4 扩展 | JS 沙箱兜底 + 更多预置平台 + 打包发布 | 脚本模板可导入导出；Windows 安装包 + 自动更新 |

每个里程碑遵循 TDD：先契约测试后实现（网络一律 mock）。

### 审查遗留备忘（随对应里程碑处理）

2026-08 核心业务两轮审查后遗留的低优先级事项：

- **M2 模板 DSL 时**：自定义 URL 支持后，`HttpRequest` 的 Debug 输出需对 URL query 部分打码（用户可能把 key 写进 query string）；同进程多线程并发保存配置需调用方串行化（tmp 名仅含 pid）。
- **按需**：错误体解析可补充支持 `{"error": "plain string"}` 平铺形态（one-api 系少数端点）。
